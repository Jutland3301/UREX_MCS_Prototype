1. SYSTEM OVERVIEW
==================

The UREX Ground System is expected to consist of multiple hardware and software
components that exchange telemetry, commands, events, and status information.

High-level software/hardware chain:

    Satellite / Radio / CAN / SDR / Other Hardware
                        |
                        v
                 Raspberry Pi
                        |
                        | Ethernet
                        | ZeroMQ / MQTT
                        v
                Mission Control System
                      (MCS)

Main software responsibilities:

Raspberry Pi side:
- Interface with hardware devices.
- Receive telemetry/data from connected hardware.
- Convert hardware data into agreed software message/packet formats.
- Perform local validation where required.
- Forward telemetry/events to the MCS.
- Receive commands from the MCS.
- Validate and dispatch commands to the correct hardware interface.
- Produce ACK/NACK/status responses.
- Maintain local health/status information.
- Support logging and fault reporting.

MCS side:
- Connect to Raspberry Pi/software endpoints.
- Receive telemetry, events, acknowledgements, and error messages.
- Validate packet/message structure and CRC where applicable.
- Convert received data into internal telemetry models.
- Display telemetry and system status in the PySide6 GUI.
- Provide packet monitoring and event/error logging.
- Allow operators to issue commands.
- Track command status and responses.
- Support ZeroMQ first, with MQTT replaceable through the same communication
  abstraction.
- Support simulator operation without real hardware.

Simulator side:
- Emulate hardware/Raspberry Pi input and output behaviour.
- Produce realistic time-varying telemetry.
- Support deliberate fault/error injection.
- Follow the same interface/packet definitions used by real hardware/software.

3. DATA FLOW TYPES
==================

The system shall distinguish at least the following message/data classes:

1. TELEMETRY
   Periodic or event-driven engineering/system measurements.

2. EVENT
   Informational state changes, transitions, or notable occurrences.

3. WARNING
   Non-critical abnormal condition.

4. ERROR
   Failed operation, invalid packet, communication failure, hardware fault,
   or other error condition.

5. COMMAND
   Operator-generated request sent from MCS toward Raspberry Pi/hardware.

6. ACK
   Positive acknowledgement that a command was accepted/processed.

7. NACK
   Negative acknowledgement indicating rejection or failure.

8. HEARTBEAT
   Periodic indication that a software/hardware endpoint is alive.

9. RAW / DEBUG DATA
   Optional raw frames or diagnostic information for engineering use.

10. CRC / VALIDATION / ERROR HANDLING
=====================================

10.1 CRC

Final CRC definition:
- Algorithm: TBD
- Polynomial: TBD
- Initial value: TBD
- Reflection: TBD
- XOR-out: TBD
- Endianness: TBD
- Covered bytes: TBD

10.2 Validation order

Recommended order:

1. Receive raw message.
2. Validate minimum length.
3. Validate protocol version.
4. Validate message type.
5. Validate declared payload length.
6. Validate CRC.
7. Validate packet/message ID.
8. Parse payload.
9. Validate field ranges where applicable.
10. Convert to internal telemetry/command model.
11. Forward to GUI/logging/business logic.

10.3 Invalid packet handling

Invalid packets shall:
- Not crash the receiver.
- Produce an error/event log entry.
- Increment appropriate counters.
- Preserve raw packet data where useful for debugging.
- Be rejected from normal telemetry processing when integrity is not trusted.


11. SIMULATOR REQUIREMENTS
==========================

The simulator is not only a random data generator.

It shall emulate the same interfaces used by the real system.

11.1 Normal behaviour

Telemetry values should:
- Start from realistic nominal values.
- Change gradually over time.
- Respect configured physical/engineering ranges.
- Use the same packet/message definitions as real data.
- Maintain sequence counters.
- Maintain timestamps.
- Produce valid CRC by default.
- Support realistic state transitions.

11.2 Fault injection

The simulator should allow deliberate injection of:

- CRC error
- Invalid packet length
- Invalid packet ID
- Packet loss
- Duplicate packet
- Out-of-order packet
- Delayed packet
- Communication timeout
- Raspberry Pi disconnect
- Radio disconnect
- Low RSSI
- Low SNR
- CAN error
- CAN bus-off
- SDR overrun
- High temperature
- Low/high voltage
- Invalid command
- NACK response
- Missing ACK
- Software process failure

18. IMPLEMENTATION RULE
=======================

Until the above team-level interface definitions are agreed:

- Code may use placeholders and clearly marked TBD values.
- Do not hard-code assumed hardware specifications as final.
- Do not let GUI-specific decisions define protocol formats.
- Do not let simulator-specific decisions define real hardware interfaces.
- Shared definitions should become the single source of truth once agreed.
- Raspberry Pi, simulator, communication, packet parser, and MCS GUI should all
  consume the same shared definitions.
