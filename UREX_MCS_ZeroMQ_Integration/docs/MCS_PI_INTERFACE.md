# UREX MCS–Raspberry Pi Interface v1.0

Date: 12 October 2026. Software-side integration specification for Patrick, Yucheng and Vito.

This document fixes the interface to implement. It carries forward the agreed Protobuf/UX framing. The integration schema and operating defaults below are newly specified here; they are not a claim that the existing simulator already implements them or that hardware-side implementation has been approved. The simulator release number and the interface version are separate.

## 1. Scope and architecture

Hardware-specific radio/CAN/SDR frames → Pi adapter → this interface → MCS decoder → GUI and SQLite/JSONL logs. The reverse direction carries MCS transmit requests and Pi command results. Pi normalizes hardware data; SQLite/JSONL files are generated by MCS, not transmitted as the network format.

The radio payload is opaque binary. Pi must preserve its bytes exactly. Hardware-native CRC/FEC remains on the hardware path and is separate from the application CRC below. A Pi TX completion means local hardware transmission completed; it does not prove spacecraft reception.

## 2. Network-independent frame

One MQTT or ZeroMQ transport message contains exactly one complete frame. No newline, NUL terminator, ASCII hex, JSON or Base64 wrapper. Do not concatenate frames or split one frame across application messages.

| Offset | Field | Bytes | Encoding |
|---:|---|---:|---|
| 0 | Magic | 2 | `55 58` (ASCII `UX`) |
| 2 | Frame version | 1 | `01` |
| 3 | Body length N | 4 | Unsigned integer, big-endian; counts only Protobuf body |
| 7 | Body | N | Serialized `urex.integration.v1.IntegrationPacket` |
| 7+N | CRC | 2 | CRC-16/CCITT-FALSE, big-endian |

Total length = N+9. Integration body limit = 65,536 bytes. CRC covers all bytes from magic through the last body byte, including version and length. CRC parameters: polynomial `0x1021`, initial value `0xFFFF`, RefIn=false, RefOut=false, XorOut=`0x0000`; check for ASCII `123456789` = `0x29B1`. Protobuf uses its native wire encoding; the big-endian rule applies only to the outer length and CRC.

Reject bad magic/version, N=0, oversize bodies, length mismatch, bad CRC, malformed Protobuf or a missing/invalid known message body. Log the rejection and do not update GUI telemetry or execute a command. Unknown Protobuf fields are ignored for compatible extension; unknown body alternatives are logged and ignored.

## 3. Shared schema

The namespace below avoids silently repurposing unknown existing simulator field numbers. Merge this schema into the implementation while retaining the existing simulator schemas. Both ends must generate bindings from exactly this definition. Interface semantic version is 1 and frame version remains 1.

```proto
syntax = "proto3";
package urex.integration.v1;

message IntegrationPacket {
  uint32 schema_version = 1;   // Must be 1.
  string session_id = 2;       // UUID string, new for each sender process start.
  uint64 sequence = 3;         // Starts at 1; increases across all sender messages.
  uint64 timestamp_unix_ms = 4;// Sender event time, UTC Unix milliseconds.
  oneof body {
    TransmitRequest transmit_request = 10;
    CommandResult command_result = 11;
    RadioReceive radio_receive = 12;
    Status status = 13;
  }
}

message TransmitRequest {
  string command_id = 1;       // UUID string; stable for the same logical request.
  bytes payload = 2;
}

enum CommandState {
  COMMAND_STATE_UNSPECIFIED = 0;
  ACCEPTED = 1;
  TX_COMPLETED = 2;
  FAILED = 3;
  REJECTED = 4;
}
message CommandResult {
  string command_id = 1;
  CommandState state = 2;
  string error_code = 3;       // Empty on success; stable machine-readable code.
  string error_message = 4;    // Human-readable explanation.
}

message RadioReceive {
  bytes payload = 1;
  optional float rssi_dbm = 2;
  optional float snr_db = 3;
  optional bool radio_crc_ok = 4;
}

enum Component {
  COMPONENT_UNSPECIFIED = 0;
  PI = 1;
  RADIO = 2;
  SDR = 3;
  CAN = 4;
  SPACECRAFT = 5;
}
enum Health {
  HEALTH_UNSPECIFIED = 0;
  INITIALIZING = 1;
  READY = 2;
  DEGRADED = 3;
  ERROR = 4;
  UNAVAILABLE = 5;
}
message ComponentStatus {
  Component component = 1;
  Health health = 2;
  string error_code = 3;
  string error_message = 4;
  string configuration_summary = 5;
}
message Status {
  repeated ComponentStatus components = 1;
  uint32 max_tx_payload_bytes = 2; // Effective hardware-path limit, excluding UX envelope.
  bool clock_synchronized = 3;
}
```

Session ID, nonzero sequence, nonzero timestamp and exactly one body are mandatory at application validation. Command IDs must be valid UUID strings. Payload must be nonempty. Reject unspecified command/component/health values; future unsupported values are logged rather than interpreted as healthy. RSSI/SNR, if present, must be finite. Unknown measurements are absent, never replaced with zero. An absent radio CRC result means unavailable information, not success.

The four bodies have fixed directions:

| Body | Direction | Event timestamp meaning |
|---|---|---|
| TransmitRequest | MCS → Pi | MCS created the request |
| CommandResult | Pi → MCS | Pi entered the reported command state |
| RadioReceive | Pi → MCS | Pi first received the complete payload from the hardware interface |
| Status | Pi → MCS | Pi sampled the status |

Pi receive time is not claimed to be spacecraft transmit time or RF arrival time. MCS additionally records its own UTC receive time and uses a local monotonic clock for timeout/latency intervals. Cross-machine one-way latency is valid only when clocks are synchronized; preserve timestamps even when they are not.

## 4. Command behavior and duplicates

Pi validates the frame, command ID, payload size and hardware readiness. A valid executable request returns ACCEPTED, followed by exactly one terminal state: TX_COMPLETED or FAILED. A request refused before acceptance returns REJECTED. A local write to a UART alone must not be reported as TX_COMPLETED; use the hardware TX-done result. If that signal is unavailable, report FAILED with TX_CONFIRMATION_UNAVAILABLE rather than inventing completion.

Standard error codes: HARDWARE_BUSY, INVALID_REQUEST, PAYLOAD_TOO_LARGE, HARDWARE_NOT_READY, ID_CONFLICT, TX_FAILED, TX_TIMEOUT, TX_CONFIRMATION_UNAVAILABLE. Error text supplies the component-specific detail. Unparseable/corrupt frames cannot safely produce a correlated response and are logged locally.

Pi keeps command ID, exact payload bytes and latest result for 10 minutes, retaining pending commands until resolved. A duplicate ID with identical bytes replays the latest result without transmitting again. A duplicate ID with different bytes returns REJECTED/ID_CONFLICT without altering the original command. On Pi restart the cache is lost and session ID changes: MCS must not automatically resend unresolved requests. This is bounded duplicate suppression, not a durable exactly-once guarantee.

MCS default acceptance timeout = 2 seconds; completion timeout = 3 seconds after acceptance. Expiry displays OUTCOME_UNKNOWN locally, because a late or lost response does not prove TX failure. Late valid results update that command. No automatic application retry of a transmit command. A user-requested new transmission gets a new command ID.

## 5. Status, limits and receive behavior

Pi sends Status immediately on connection, every 1 second, and on a component health/configuration change. Status is a full snapshot of the five named components; report missing components as UNAVAILABLE. Spacecraft health is based on actual available evidence, not inferred as READY from a healthy Pi. MCS marks status stale after 3 seconds without Status, without rewriting the last reported hardware health.

Initial max_tx_payload_bytes = 63, carrying forward the reported current UART message limit. This is an initial adapter setting, not a verified universal radio limit. Hardware owners must supply the effective limit before live TX; Pi publishes it in Status and enforces the real lower bound. MCS refuses TX until it has a current Status and then uses the published limit. The old 63+terminator rule belongs only to its native hardware adapter: the terminator is not appended to UX frames. RX payload can have a different hardware limit; the full serialized network body must still fit 65,536 bytes. SDR IQ/bulk data uses a separate future interface.

Pi forwards each valid received payload immediately, preserving order from its hardware input. Do not silently aggregate into periodic telemetry snapshots. Corrupt native frames must not appear as normal successful RadioReceive events; record native CRC errors in component status/error reporting. If only a filtered stream is available from RadioLib, omit radio_crc_ok unless a per-frame result is actually known.

Each sender serializes its outbound sequence assignment. Receivers detect duplicates by (session_id, sequence), and log sequence gaps/reordering. A repeated network delivery of the same frame must not create a second GUI/log event. Sequence gaps are diagnostics: they do not request radio retransmission. Command duplicate protection additionally uses command_id across MCS sessions.

## 6. ZeroMQ adapter

MCS uses ROUTER and binds TCP port 5557; one Pi uses DEALER and connects to MCS. Pi routing identity is `urex-pi`. There is one Pi per MCS endpoint. For same-PC testing MCS may bind `tcp://127.0.0.1:5557`; for LAN integration bind the MCS LAN IP or `tcp://*:5557`, and Pi connects to `tcp://<MCS-IP>:5557`. Pi sends Status immediately (or the next one-second publication if connection is still establishing), so MCS learns its route without an extra application message type.

DEALER sends exactly one application frame. ROUTER sees `[routing identity, application frame]`; the identity is ZeroMQ routing metadata and is not part of UX/Protobuf/CRC. No REQ/REP empty delimiter. Both sides use bounded 1000-message queues and LINGER=0. Pi uses IMMEDIATE=1, reconnect intervals of 250 ms up to 2 seconds, and transport heartbeats. Valid periodic Status is the application liveness signal. Connecting or binding a socket alone does not establish hardware readiness. Reconnection does not resend application TX requests.

The native hardware app owns RadioLib/SPI/GPIO and its TX/RX workers. The C++ service owns one DEALER on one networking thread; hardware workers exchange events through thread-safe queues. Python mock code is a reference/testing backend, not the production GPIO driver. Both implementations preserve this schema. Cache capacity is 4096 commands; cache-full requests are rejected with HARDWARE_BUSY without sacrificing retained duplicate protection.

## 7. Implementation handoff and acceptance

Vito: implement the MCS network interface, codec integration, timestamps, command tracking and GUI/SQLite/JSONL mapping in coordination with them. The transport comparison remains a separate task from packet schema adoption.

Before live hardware integration, both ends must pass: a shared serialized frame decoded to identical values; bad CRC/length/version rejection; payload boundary rejection; absent RSSI/SNR preservation; ACCEPTED→TX_COMPLETED and ACCEPTED→FAILED; duplicate request without second TX; duplicate-ID/different-payload conflict; Pi restart with unresolved command displayed as unknown; stale status indication. Software implementation and mock validation are included in this branch. No native hardware-driver integration or hardware acknowledgment is implied.
